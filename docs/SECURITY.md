# Security model and verification

Supabase Auth owns password hashing, verification and session tokens. Only URL and publishable key are exposed in the Vite bundle. Local `.env.local`, `.netlify/`, build output and Playwright output are ignored. Never put a service-role key in any `VITE_` variable.

Every ResearchFlow public table has RLS. Membership is checked in a non-exposed schema to avoid recursive membership policies. Definer functions have empty search paths, explicit user checks and revoked anonymous execution. Workspace creation is atomic and requires a verified account. Role changes cannot be written directly. Invitation acceptance locks the row and checks the current verified Auth email, unused state and expiry. Public wrappers are security invoker.

Database triggers preserve workspace IDs and creator IDs and restrict member task updates to status changes. Member self approval is rejected; completed tasks are locked to leaders. Composite foreign keys prevent foreign-team phase/assignee injection. The founding leader remains a leader. Audit logs are generated by triggers and cannot be modified by the browser.

Storage is private, MIME/size limited and workspace scoped. Fresh logo paths avoid destructive overwrites. Removing a workspace member removes access immediately through database membership checks, without relying on cached role claims.

Static hosting sends CSP, frame denial, MIME-sniffing prevention, referrer and permissions policies. React escapes text; no raw HTML injection is used. Browser-stored sessions remain subject to XSS, so dependency and CSP controls are material. Public bundles contain no research records.

Automatic approval review rejected changing that legacy behavior; the owner chose to leave it unchanged. It is not used for ResearchFlow authorization, but runs on signup in this shared project.
- Legacy tables with enabled RLS and no policy are deny-by-default; informational advisor findings do not authorize opening them.
- Email delivery, SMTP, email confirmation enforcement, redirect allowlist, abuse protection, leaked-password protection, backup/retention and operational monitoring must be checked in Supabase before a broad production rollout.
- Auth logs previously confirmed `over_email_send_rate_limit`. Brevo SMTP was subsequently configured, its login corrected, and a real password-reset API request succeeded. Inbox delivery still requires recipient confirmation. Client retry controls do not raise server quotas; email verification remains enabled.
- No independent penetration test, compliance certification or production-readiness claim is made.
- MVP 2 adds document permissions and review evidence. MVP 3 adds confidential dataset governance and in-app notifications; outbound channels remain future scope.

Run `supabase/tests/isolation.sql` as postgres. It creates synthetic accounts inside one transaction, executes checks as `authenticated`, tests ID/role boundaries and rolls everything back. Do not remove RLS to troubleshoot client errors.

## MVP 2 authorization

All new tables deny anonymous access and direct browser DML. The invoker RPC calls a private-schema, empty-search-path definer implementation with current membership, role, ownership, type/length and cross-resource checks. Identity and role come from `auth.uid()` and membership rows, never editable metadata. RLS restricts all reads; signed file access uses the same document/channel/workspace boundaries. Channels are workspace-wide; archiving prevents new messages. Message deletion is a soft deletion with the body removed, and file access is withdrawn.

Restricted-document ACLs cover metadata, versions, comments, submissions, reviews and Storage. Leaders/supervisors/creator and explicitly assigned readers may access restricted documents. Upload paths must match the authenticated workspace/user and random filename; existing objects cannot be overwritten. Server bucket and registration checks validate declared MIME, extension and byte length. These checks are not antivirus or content classification. Failed unregistered uploads can be cleaned up only by their uploader. Registered files cannot be deleted through that cleanup path, including after reader revocation.

Only assigned supervisors make academic decisions; only leaders make internal decisions. Requesters cannot review themselves. Original document creators and version authors cannot academically approve their own research even after role reassignment. Review decisions are append-only; phase review state cannot be changed through direct authenticated updates. Workspace locks, composite foreign keys, unique pending requests and action-row locks enforce atomic invariants.

Short-lived signed URLs expire after 60 seconds; revoking membership or ACL prevents new links immediately but does not invalidate already-issued URLs or downloaded copies. No raw HTML/Markdown rendering occurs. Meeting links allow HTTP/HTTPS only. Realtime events remain RLS protected; reconnect refreshes recover missed events. General audit stores only operation/resource/actor/time, not filenames, document contents or message text.

The security advisor reported no new MVP 2 table/function warnings. Existing legacy trigger and Auth leaked-password-protection findings remain documented and unchanged per the owner's prior instruction. This is not an independent penetration test or compliance certification.

Existing advisor references: [mutable search path](https://supabase.com/docs/guides/database/database-linter?lint=0011_function_search_path_mutable), [anonymous definer execution](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable), [authenticated definer execution](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable), and [leaked-password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

## MVP 3 authorization and privacy
Independent academic section decisions require a supervisor, a submitted section and a reviewer who is not the paper creator, section assignee or linked draft's original creator/author. Current membership rows, never editable Auth metadata, authorize operations. Dataset metadata, snapshots and versions share a current-membership/reader predicate; leader, supervisor, creator, assigned researcher and explicitly allowed readers may access restricted entries.

Dataset Storage has no authenticated SELECT/signing policy. The Edge Function verifies the real Auth user, caller-scoped workflow/RLS permission, permission state, retention and status before signing an authorized DB path for 60 seconds. The browser cannot choose a longer expiry. Already-issued URLs last until expiry; downloaded copies cannot be revoked. External hosts enforce their own permissions and expiry. Access logs record authorization/link issuance, not proof of bytes consumed or every reuse.

Notifications contain generic summaries without private research contents and cannot be forged by browser writes. Users change only their own reads/preferences. Paper notes are workspace-shared even if a linked draft is restricted. Reports load fresh authorized rows and run locally; raw dataset bytes are excluded. CSV formula prefixes and BibTeX control syntax are escaped. GitHub links accept only validated HTTPS GitHub types; no tokens are collected.

File MIME/size/extension checks are not antivirus or automated data classification. Registry entries and Granted labels are not legal permission. Failed dataset registrations can leave an orphan needing privileged Storage API cleanup; retention/orphan purge is not scheduled. An empty Storage removal response does not prove bytes were deleted. Legacy Auth warnings remain unchanged by owner choice.
